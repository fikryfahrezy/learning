# Section 6 — Creating a Production-Grade Workflow

Summary of lectures 67–90. The section starts a workflow that runs from development through testing
to deployment, and it has to keep working through later rounds of changes and redeploys. The
project is a pre-generated **React** app (`frontend`). The section wraps it in Docker in three ways:
a **development image** (`Dockerfile.dev`) with **volumes** so code changes show up live, a
**test setup** (run with `docker run -it`, `docker exec` or a second Compose service), and a
**production image** (`Dockerfile`) that uses a **multi-step build**: Node builds the app, then
**NGINX** serves the static output. Lecture 90 adds a **Vite** version of the same project.

> **Docker is not a requirement for this workflow.** The instructor used the same GitHub → Travis
> CI → AWS flow at several startups with no Docker at all. *"Docker is just a tool that's going to
> make executing some of these tasks a lot, lot easier."* The Docker side comes down to **two
> Dockerfiles**: `Dockerfile.dev` for development and tests, and `Dockerfile` for production.

---

## 67. Development Workflow

The section so far has covered containers, images, the Docker CLI and Docker Compose. It hasn't
covered how to use Docker in a **production-type environment**: how to develop an app with Docker
and then push it to an outside host such as **AWS** or **DigitalOcean**.

"Flow" here means the whole cycle: **develop → test → deploy**, then later **develop more, test
again and redeploy**.

> *"No app gets deployed one time."* Any flow has to support further development, testing and
> redeployment later on.

## 68. Flow Specifics

This lecture covers the outside services first. How Docker fits in comes in the next lecture.

### The GitHub repository

A **GitHub repository** is the central coordination point for the code. It has two branches:

| Branch | Role |
| --- | --- |
| **feature** | The development branch. This is where you add code and make changes. |
| **master** | The **clean working copy** of the code base. Changes merged here are **deployed automatically** to the hosting provider. |

### The flow

1. On your local machine, **pull** the latest code from the **feature** branch. Another engineer
   might have pushed code there already.
2. Make your changes, then **push** them back to the **feature** branch. **You never push
   directly to master.**
3. Open a **pull request** to merge feature into master.
4. The pull request sends the code to **Travis CI**, a **continuous integration provider**. It
   pulls the code and **runs the tests** you've written. This project only uses the few tests that
   come pre-generated.
5. If the tests pass, the PR is merged into master. Travis CI runs the tests again and then
   **deploys automatically to AWS**, specifically **Elastic Beanstalk**.

### The same flow in three phases

| Dev | Test | Prod |
| --- | --- | --- |
| Make changes on the feature branch, push to GitHub, open a PR to master | Travis CI pulls the code and runs the tests | After the merge, Travis CI tests again and deploys to AWS Elastic Beanstalk |

## 72. Necessary Commands

Three commands come up again and again in this workflow:

| Command | Purpose |
| --- | --- |
| **`npm run start`** | **Development only.** Starts a **development server** that hosts the app in the browser. It is *not* appropriate for production. |
| **`npm run test`** | Runs the project's tests. CRA generates one or two tests, and no more are added. The point is to **deploy only when all tests pass**. |
| **`npm run build`** | Builds a **production version**. It takes all the JavaScript files and concatenates them into a single file that can be served in production. |

### Trying them

```sh
npm run test     # starts the test runner; one test passes. Press q to exit.
npm run build    # "Creating an optimized production build..."
npm run start    # opens localhost:3000 with the default React app
```

After `npm run build` there's a new **`build/`** directory with an **`index.html`** and a
**`static/`** directory. Somewhere inside `static/` is the JavaScript file that *is* the app.
These are the files that eventually need to be served from AWS.

Other stacks have the same three kinds of command. `npm run start` is like `rails s`, and
`npm run build` is like `go build`. Each stack has one command for development, one for tests and
one to get ready for production.

## 73. Creating the Dev Dockerfile

There will be **two Dockerfiles**:

| File | Used for |
| --- | --- |
| **`Dockerfile.dev`** | Running the app in **development** (and later, running tests) |
| **`Dockerfile`** | **Production** (written in lecture 88) |

### `Dockerfile.dev`

Put together from the lecture's narration, since `frontend.zip` doesn't include it:

```dockerfile
FROM node:alpine

WORKDIR '/app'

COPY package.json .
RUN npm install

COPY . .

CMD ["npm", "run", "start"]
```

It's the same pattern as earlier projects. Copy `package.json` first so the `npm install` layer is
cached, then copy everything else, then start the dev server.

### Building with a custom file name

`docker build` always looks for a file called exactly **`Dockerfile`**, so a plain build fails:

```sh
docker build .                     # error: no Dockerfile found
docker build -f Dockerfile.dev .   # -f names the file to build from
```

**`-f`** specifies the file used to build the image. Warnings during the build are fine. Only
worry about output that specifically says **error**.

## 76. Docker Volumes

### Why the copy is the problem

`COPY . .` copies `src/`, `public/` and everything else into `/app` in the temporary container used
while building the image. That's a **snapshot locked in time**, and it doesn't update when the code
changes. The fix is to **change the `docker run` command** and use **Docker volumes** instead.

### What a volume is

A **volume** puts a **reference** (a placeholder) inside the container that **points back to
folders on the local machine**. It works a lot like a port mapping:

| Mapping | From → to |
| --- | --- |
| **Port mapping** (`-p`) | port inside the container → port outside |
| **Volume** (`-v`) | folder inside the container → folder outside |

Volumes weren't used earlier because the syntax is *"a little bit of a pain in the rear"*.

### The full command

```sh
docker run -p 3000:3000 -v /app/node_modules -v $(pwd):/app <image-id>
```

- **`-v $(pwd):/app`**: **`$(pwd)`** expands to the **present working directory** (run `pwd` to
  see it). It maps the whole `frontend` folder to `/app` in the container.
- **Windows:** `$(pwd)` does **not** work in Command Prompt or PowerShell. It does work in
  **Git Bash**. See lecture 77.
- The first switch, `-v /app/node_modules`, has **no colon**. It's explained in lecture 78.

### Running without the first switch

```sh
docker build -f Dockerfile.dev .
docker run -p 3000:3000 -v $(pwd):/app <image-id>
```

The React project tries to start and fails with a **`react-scripts` not found** error. The
instructor leaves it out on purpose to show why the extra switch is needed.

## 77. WSL and Windows Users Must Read Before Next Lecture

This note covers fixes for **volume issues** and **file watchers not picking up changes** on
Windows. Read it in full before continuing.

### Solution #1 (quickest)

This one **only fixes reloading of the web app**. **It does not help re-run the tests.** It assumes
the project is on the **Windows file system**, not the WSL Linux file system. It uses an
undocumented Webpack setting
([create-react-app#12397](https://github.com/facebook/create-react-app/issues/12397)).

1. Add the variable to the `start` script in `package.json`:

   ```json
     "scripts": {
       "start": "WATCHPACK_POLLING=true react-scripts start",
   ```

2. Build the image as usual:

   ```sh
   docker build -f Dockerfile.dev -t USERNAME:frontend .
   ```

3. From the project root, run the container **in PowerShell**:

   ```sh
   docker run -it -p 3000:3000 -v /app/node_modules -v ${PWD}:/app USERNAME:frontend
   ```

   Use **`${PWD}`**, the PowerShell form, and not the `pwd` from the videos.

### Solution #2 (best practice)

This is the only fix for **both** app reloading **and** re-running tests. With WSL running Docker
Desktop, the project should live on the **Linux file system** and **every Docker command should
run inside WSL**
([Docker's WSL best practices](https://docs.docker.com/desktop/windows/wsl/#best-practices)). If the
project is on the Windows file system, volumes may not work and performance may suffer badly.

1. Open your WSL distribution (Ubuntu by default) from the search in the system tray. The terminal
   opens in the home directory on the Linux file system.
2. Run `explorer.exe .` to open a file browser at `/home/USERNAME`, then move the `frontend`
   folder into it.
3. `ls` to check, then `cd frontend`. The path should be `/home/USERNAME/frontend`.
4. **Delete any `node_modules` or `package-lock.json`**. If they were generated on Windows and
   copied over, they will conflict.
5. Change `Dockerfile.dev` to use **`node:lts-alpine`**:

   ```dockerfile
   FROM node:lts-alpine

   WORKDIR '/app'

   COPY package.json .
   RUN npm install

   COPY . .

   CMD ["npm", "run", "start"]
   ```

6. Build from the WSL terminal:

   ```sh
   docker build -f Dockerfile.dev -t USERNAME:frontend .
   ```

7. Run from the WSL terminal. **Don't use a PWD variable**. Use `~` or type the full path:

   ```sh
   docker run -it -p 3000:3000 -v /app/node_modules -v ~/frontend:/app USERNAME:frontend
   # or
   docker run -it -p 3000:3000 -v /app/node_modules -v /home/YOURUSERNAME/frontend:/app USERNAME:frontend
   ```

8. From now on, **run all Docker commands and projects inside WSL**, not Windows.

### Opening the WSL folder in VS Code

- **Option 1:** VS Code's
  [Remote – WSL](https://code.visualstudio.com/docs/remote/wsl#_open-a-remote-folder-or-workspace)
  "open a remote folder" feature.
- **Option 2:** in the project folder, run `explorer.exe .`, copy the location path, then in VS
  Code choose **File → Open Folder**, paste the WSL address and click **Select Folder**.

## 78. Bookmarking Volumes

### Why `react-scripts` wasn't found

`-v $(pwd):/app` says *everything* in `/app` comes from the local folder. But the local folder has
**no `node_modules`**, because it was deleted in lecture 74. So the container's own `node_modules`
(installed by `RUN npm install`) got **overridden** by a reference pointing to *"essentially
nothing"* on the local machine.

### The fix: a volume with no colon

```sh
docker run -p 3000:3000 -v /app/node_modules -v $(pwd):/app <image-id>
```

| Syntax | Meaning |
| --- | --- |
| **`-v <host>:<container>`** (with a colon) | **Map** a folder inside the container to a folder outside it |
| **`-v <container path>`** (no colon) | A **placeholder / bookmark**: *"this folder set in stone, don't try to mess with it"*. Don't map it to anything. |

So `/app/node_modules` stays the container's own copy, and everything else in `/app` comes from the
local machine.

### Live updates

Run it, open `localhost:3000` and *"Hi There"* appears. Change `src/App.js` to *"Bye There"* and
save, and the page **updates on its own** (refresh by hand if it doesn't).

- The automatic refresh is a **feature of create-react-app**, not Docker.
- Docker's job is to **pass local file changes into the running container**, so the React dev
  server can see them.

## 79. Shorthand with Docker Compose

The only downside of volumes is the *"ridiculously long"* `docker run` command: a port, two volumes
and an image ID. **Docker Compose** exists to make `docker run` easier, and it helps **even with a
single container**.

### First attempt at `docker-compose.yml`

```yaml
version: '3'
services:
  web:
    build: .
    ports:
      - "3000:3000"
    volumes:
      - /app/node_modules
      - .:/app
```

- The service name is up to you (`react-app`, `web`, …). The instructor goes with **`web`**.
- **`ports`**: local 3000 → container 3000.
- **`volumes`** is the shorthand for the two `-v` flags:
  - `/app/node_modules`: the placeholder, so don't map anything over it.
  - `.:/app`: **`.`** is the current directory, mapped to `/app` inside the container.

```sh
docker-compose up
```

This fails with **"Cannot find a Dockerfile"**. `build: .` looks for a file named `Dockerfile`, and
the project only has `Dockerfile.dev`.

## 80. Overriding Dockerfile Selection

Replace `build: .` with two options:

```yaml
version: '3'
services:
  web:
    build:
      context: .
      dockerfile: Dockerfile.dev
    ports:
      - "3000:3000"
    volumes:
      - /app/node_modules
      - .:/app
```

| Option | Meaning |
| --- | --- |
| **`context`** | Where the **files and folders** for the image come from. `.` means the directory holding the compose file. If the React project were in a subfolder, you'd name that folder. |
| **`dockerfile`** | Which Dockerfile to build with. It's looked up relative to the context. |

`docker-compose up` now builds successfully and runs `npm install`.

## 82. Executing Tests

Running the tests in development is simple: build the dev image and **override the default
command**.

```sh
docker build -f Dockerfile.dev .
docker run <image-id> npm run test
```

The test runner starts and shows its **interactive menu**, but pressing **Enter does nothing**. By
default, `docker run` only connects you to the container's **stdout**. To send input you also need
**stdin**, which means **`-it`**:

```sh
docker run -it <image-id> npm run test
```

Now it's fully interactive, with a proper full-screen view:

- **Enter**: re-run all tests
- **w**: show the menu
- **p**: filter by file name (for example `app` matches `App.test.js`)
- **q**: quit
- **Ctrl+C**: exit

(The instructor loses the image ID twice here and notes, *"this is why you're supposed to use
tags"*.)

## 83. Live Updating Tests

### Same snapshot problem

In `src/App.test.js`, copy the `it`/`test` block and paste a second copy below it, then save. The
test runner **doesn't re-run**, and pressing Enter still shows **one test**. The container made by
`docker run … npm run test` has **no volumes**, so it's using the stale snapshot.

Two ways to fix it: a **second Compose service** (next lecture), or first:

### Approach 1: `docker exec` into the Compose container

```sh
docker-compose up                 # terminal 1: the web container, with volumes
docker ps                         # terminal 2: get its ID
docker exec -it <container-id> npm run test
```

This **reuses the running container**, which already has the volumes. It shows **two tests**.
Delete the duplicate block and save, and it goes back to one test on its own.

- **Upside:** live updates **and** full interactivity.
- **Downside:** you have to start Compose, look up the container ID and remember the `docker exec`
  command. That's hard to remember off the top of your head.

## 84. Docker Compose for Running Tests

### Approach 2: a dedicated test service

The instructor adds a second service whose only job is to run the tests. In the audio its name
sounds like "Tes". The Vite zip (lecture 90) calls it **`tests`**, and that name is used here:

```yaml
version: '3'
services:
  web:
    build:
      context: .
      dockerfile: Dockerfile.dev
    ports:
      - "3000:3000"
    volumes:
      - /app/node_modules
      - .:/app
  tests:
    build:
      context: .
      dockerfile: Dockerfile.dev
    volumes:
      - /app/node_modules
      - .:/app
    command: ["npm", "run", "test"]
```

- Same **`build`** and **`volumes`** as `web`.
- **No `ports`**. The test suite runs no server.
- **`command`** overrides the Dockerfile's `CMD`, so this service starts with `npm run test`
  instead of `npm run start`. The `["npm", "run", "test"]` bracket form is *"not the same type of
  array"* as a YAML dash list, just a different notation.
- Watch the YAML indentation: one level before `tests`, two before its options.

```sh
docker-compose up --build
```

`--build` isn't strictly needed since no files changed, but *"sometimes when you add on a new
service it can be a little bit finicky"*. Both the test output and the "view in browser" message
appear. Duplicate the test block and save, and the suite **re-runs with two tests**.

- **Downside:** the test output is mixed into Compose's log output, and **there's no way to send
  stdin**. Enter, `w` and the other keys do nothing.

## 85. Shortcomings on Testing

### Why keystrokes don't reach the test runner

- Each container starts with a **primary command** (`npm run test` for tests, `npm run start` for
  web).
- **stdin, stdout and stderr are per process.** Nothing forwards what you type in the Compose
  terminal to the test container's stdin, and Compose can't easily be set up to do it.

### Trying `docker attach`

```sh
docker ps                          # second terminal: get the test container's ID
docker attach <container-id>
```

`docker attach` forwards your terminal to the container's **primary process**. Pressing `p`, `q`,
`t` or `w` still does nothing.

> *"Unfortunately, this is as good as it gets with the Docker Compose solution for running our
> tests."*

### Looking at the processes

```sh
docker exec -it <container-id> sh  # a third terminal: open a shell in the container
ps                                 # list processes
```

| PID | Process |
| --- | --- |
| **1** | **`npm`** |
| other | `react-scripts … start.js`-style processes started by npm |

`npm run test` doesn't run the tests directly. The **`npm`** process reads `run test` and **starts
a second process** that actually runs the suite and reads keystrokes. The instructor admits they
don't know which of the two it is. **`docker attach` always attaches to PID 1**, the `npm` process,
never to the secondary one, so the keystrokes go to the wrong process.

### The trade-off

| Approach | Upside | Downside |
| --- | --- | --- |
| **Second Compose service** (`tests`) | Just run `docker-compose up` and the tests run and re-run on changes | No interactive `p` / `t` / `q` / Enter |
| **`docker exec -it <id> npm run test`** into `web` | Full interactivity | Need the container ID and have to remember the command |

Neither is ideal, so pick the one you like better. Many test suites in other languages, and some
JavaScript ones, have **no interactive mode** at all, so losing it isn't *"the worst thing in the
world"*.

## 86. Need for NGINX

### Dev vs. production serving

| Environment | Who serves `index.html` + `main.js` to the browser |
| --- | --- |
| **Development** | The **dev server** in the web container (port 3000). It processes the JavaScript and serves it, and **it's required in development**. |
| **Production** | The dev server **falls away**. `npm run build` runs **once** and produces the static `index.html` and JS file. |

The dev server isn't right for production. It spends a lot of processing on JavaScript files, and
in production the code no longer changes. Production needs a server whose **only job is to respond
to browser requests with those static files**.

### NGINX

**NGINX** is an *"extremely popular web server"* with little logic. It **routes incoming traffic
or responds with static files**, which is exactly what's needed here. A separate Dockerfile will
build a **production version of the web container** that runs NGINX and serves the build output.

## 87. Multi-Step Docker Builds

### The naive plan and its two problems

The straightforward plan: `node:alpine` → copy `package.json` → install dependencies →
`npm run build` → start NGINX. It has **two big issues**:

1. **Dependencies are only needed to build.** After the build, only the **`build/` directory**
   (`index.html`, `main.js`, …) matters. Carrying around 150+ MB of dependencies would be nice to
   avoid.
2. **Where does NGINX come from?** Nothing in this plan installs or configures it.

### Two base images

**Docker Hub** has an official **`nginx`** image (under **Explore**), and its docs have a section on
**hosting some simple content**. That's exactly the job. But Node is needed for the build too, so
**two base images** are needed. The answer is a **multi-step build**:

| Phase | Base image | Steps |
| --- | --- | --- |
| **Build phase** | `node:alpine` | Copy `package.json` → install deps → `npm run build` → produces `build/` |
| **Run phase** | `nginx` | **Copy only the `build/` folder from the build phase** → start NGINX |

> When only the build directory is copied over, *"everything else essentially gets marooned"*. The
> Node image, the installed dependencies and the source are **dropped from the final image**.

---

## 88. Implementing Multi-Step Builds

### `Dockerfile` (production)

Put together from the lecture's narration, since `frontend.zip` doesn't include it:

```dockerfile
FROM node:alpine as builder
WORKDIR '/app'
COPY package.json .
RUN npm install
COPY . .
RUN npm run build

FROM nginx
COPY --from=builder /app/build /usr/share/nginx/html
```

**Build phase:**

- **`FROM node:alpine as builder`**: **`as <name>`** tags the phase. Everything under this `FROM`
  is the **builder** phase.
- The rest is the usual setup. There are **no volumes** here: they were only for seeing live
  changes during development, and production code doesn't change, so a **straight `COPY . .`** is
  fine.
- **`RUN npm run build`** writes the output to the working directory, so the files to serve end up
  in **`/app/build`**.

**Run phase:**

- **`FROM nginx`**: a second `FROM` **starts a new phase** and ends the previous one. You don't
  need any special syntax to close it. *Each phase can only have a single `FROM` statement.*
- **`COPY --from=builder /app/build /usr/share/nginx/html`**: copies from **another phase**.
  **`/usr/share/nginx/html`** (it's `usr`, no "e") is where the NGINX image's docs say to put static
  content, and it gets served automatically.
- **No `CMD` needed.** The `nginx` image's **default command starts NGINX**.

The final image is roughly **the size of the NGINX base image**. Nothing from `node:alpine`,
`npm install` or the source code makes it in, only `/app/build`.

## 89. Running NGINX

```sh
docker build .                   # no -f: the file follows the Dockerfile convention
docker run -p 8080:80 <image-id>
```

- The build output shows `npm run build` running, then the **second step**: pulling `nginx` and
  copying from the builder phase.
- **`-p 8080:80`**: port **80** is NGINX's default in the container, mapped to **8080** on your
  machine.
- NGINX prints nothing until it gets a request, and that's normal.

Open **`localhost:8080`** and the React welcome app appears. NGINX is *"really made for production
workloads"*, so this is a solid production setup. Next up is deploying it to the outside world.

## 90. Dockerizing a React App with Vite

This lecture is only a resource: [`frontend-vite.zip`](./frontend-vite.zip), the same project built

### `Dockerfile.dev` (`frontend-vite.zip`)

```dockerfile
FROM node:lts-alpine

```

### `docker-compose-dev.yml` (`frontend-vite.zip`)

```yaml
services:
  web:
    build:
      context: .
      dockerfile: Dockerfile.dev
    ports:
      - "3000:3000"
    volumes:
      - /app/node_modules
      - .:/app
  tests:
    tty: true
    build:
      context: .
      dockerfile: Dockerfile.dev
    volumes:
      - /app/node_modules
      - .:/app
    command: ["npm", "run", "test"]
```

### `Dockerfile` (`frontend-vite.zip`)

```dockerfile
FROM node:lts-alpine AS builder
WORKDIR '/app'
COPY package.json .
RUN npm install
COPY . .
RUN npm run build

FROM nginx
EXPOSE 80
COPY --from=builder /app/dist /usr/share/nginx/html
```

```json
  "scripts": {
    "dev": "vite",
```

### What differs from the CRA version

| | CRA (lectures 67–89) | Vite (`frontend-vite.zip`) |
| --- | --- | --- |
| **Base image** | `node:alpine` | **`node:lts-alpine`** (as in lecture 77's WSL fix) |
| **Dev command** | `CMD ["npm", "run", "start"]` → `react-scripts start` | **`CMD ["npm", "run", "dev"]`** → `vite` |
| **Dev server host/port** | CRA serves on 3000 | Set in `vite.config.js`: **`host: "0.0.0.0"`, `port: 3000`**, so the dev server can be reached through the `3000:3000` mapping |
| **Test runner** | `react-scripts test` (Jest) | **`vitest`**, set up in `vite.config.js` (`jsdom` environment, `globals`, `src/setupTests.js`) |
| **Compose file** | `docker-compose.yml` with `version: '3'` | **`docker-compose-dev.yml`**, **no `version` key** |
| **Test service** | `tests` without `tty` | **`tty: true`** on `tests` |
| **Build output folder** | `/app/build` | **`/app/dist`** |
| **Phase alias** | `as builder` | `AS builder` (same meaning, uppercase) |
| **`EXPOSE`** | Not in the production Dockerfile | **`EXPOSE 80`** in the run phase |
| **React / tests** | React 18, `App.test.js` looks for "learn react" | React 19, `App.test.jsx` (Vitest `describe`/`it`) looks for "Vite + React" |

Because the compose file isn't named `docker-compose.yml`, a bare `docker compose up` won't find
it. You have to name the file, for example `docker compose -f docker-compose-dev.yml up`. The zip
doesn't include this command.

The zip also has a **`.github/workflows/deploy.yaml`** (GitHub Actions). On each push to `main` it
builds `Dockerfile.dev`, runs `docker run -e CI=true … npm test`, zips the project and deploys it
to **Elastic Beanstalk**. That covers the CI/deploy half of the workflow from lecture 68, which the
next section deals with.
